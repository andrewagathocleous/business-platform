## Known risks

- Service tokens are company-wide. An ordinary permission on a token must be held company-wide. Per-connection binding is a later hardening item.
- The sanitiser's scope is the header of `workflows/n8n/scripts/sanitize.mjs`: literal secrets in parameters and expressions are rejected, and an unparseable expression fails closed. The fixture ``={{ { `token`: `secret` } }}`` is not valid JavaScript and fails closed as unparseable. Deliberately obfuscated secrets are out of scope. Credentials belong in n8n's credential store. Only `nodes.<index>.type` may be exactly `n8n-nodes-base.<name>`, because those names are longer than the entropy limit and are not credentials. Any other `type` property is checked.
- `prisma migrate dev` must not drop the SQL-only partial unique indexes. Prisma cannot model the predicates, so they are not in `schema.prisma`: `user_identity_one_entra_key` (`user_identity (user_id) WHERE provider = 'entra'`) and `gift_message_template_one_default_key` (`gift_message_template (company_id) WHERE is_default`). RLS, grants and triggers live in `20261018234900_rls`. The printer identity unique index is in `schema.prisma`.
- Prisma 7 issues concurrent queries on one interactive-transaction client. `createPrismaClient` serialises `pg` `query` per pooled connection. Pipeline mode is not used.
- Local storage has no `openat`. `put` creates each parent, checks its real path, opens with `O_EXCL | O_NOFOLLOW`, then checks the descriptor. `get` and `exists` open with `O_NOFOLLOW`. An attacker who can already write inside `STORAGE_ROOT` is out of scope. The root must be owned by the app user with mode `0700`.
- PrimeNG 21 Toast (`p-toast` in `apps/web/src/app/app.ts`, `node_modules/primeng/fesm2022/primeng-toast.mjs`) binds `bottom` to `false` when the position is the default `top-right`: `bottom: (position is a bottom edge) && '20px'`. Angular 22 reports that as NG0318 (`[style.bottom]` bound to `false`). The warning appears in the e2e log. `node_modules` is not patched.
- This Mac has no Docker `buildx`, so Compose uses the classic builder. A parallel `docker compose build` can fail with `image "bp-api:local" already exists`, because `api` and `worker` build the same tag. The image itself builds. Build one service at a time (`build api`, `build migrate`, `build caddy`, `--profile demo build seed`) or install `buildx`.
- The Colima VM has 4 GiB. The dev stack and the local stack cannot run together, so integration tests need the local stack down. After the image build, free disk on `/System/Volumes/Data` was 14 GB, below the 15 GB gate for the next build.
- `demo-import-fixtures` can list orders before the worker container commits one it claimed while the script was draining the queue. The data is complete; only the printed summary can miss an order.
- A fresh production database has no platform owner. `compose.prod.yml` does not seed and does not enable dev login. The only writer of `is_platform_owner` is the fictional seed. That bootstrap is not implemented (P1-F). ADR-0004 names a break-glass recovery runbook. That runbook does not exist (P1-G). Neither blocks the local demo stack. Both block a real deployment.
